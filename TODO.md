# Audit findings — 2026-11-04

Audit of `master` @ `870ae95`. It builds on the November security audit (`e271f1a`) and does not repeat what that fixed. It covers auth, routing, sharing, the plugin registry and gRPC bridge, the files plugin, NC WebDAV/chunked uploads, SSH/SFTP/shell, search indexing, previews, email and server lifecycle. A second pass covered the CalDAV/CardDAV core (`internal/dav`), scheduling (iTIP/iMIP), WebDAV-Push, JMAP, and the plugin page handlers and NC-compat APIs (calendar, contacts, tasks, notes, bookmarks, feed, recipes, gallery, dashboard).

Items marked **(verified)** were reproduced with a throwaway test against the real handler stack; the rest come from reading the code. Severity is my estimate of impact and how easy each one is to exploit.

## Design patterns behind these findings

Most findings are instances of a few recurring design gaps. Fixing the pattern closes the listed items and stops new ones appearing; fixing items one at a time will not.

1. **Names and claims used as identity.** Raw strings that a user controls act as keys or credentials without being validated or proven: usernames build storage paths (C1, H9), unverified non-unique emails decide who receives and sends invitations (H14), an event UID in someone else's message selects which of your events gets overwritten (H13), per-user numeric IDs share a URL namespace that is then cached `public` (M17), and download tokens are bound to paths instead of file IDs. *Design:* key everything internally by opaque, server-issued IDs (user ID, file ID, collection ID). Validate human-readable names once, at a single boundary. Treat anything a user asserts (email, UID, ORGANIZER) as a claim that must be checked against what the server already knows.
2. **Every component writes to disk directly.** The files plugin, SFTP, SCP, the shell, notes, feed media, recipe images, calendar attachments, contact photos, gallery caches and preview caches each `filepath.Join` their own path and call `os.*`. As a result quota, metadata, search and ETags all drift (H3, H4, M6, M13, M18), and every hand-built path is a traversal risk (C1, M12). *Design:* one storage service that owns quota accounting, metadata and change events, with plugins receiving handles instead of paths. Root it in `os.Root` so traversal is impossible by construction, and add a `go tool verify` check that rejects `filepath.Join(…DataDir…)` outside that package.
3. **Security controls are opt-in per route.** CSRF (M11, raw `RegisterRoute`), auth on plugin resource routes (H10), rate limits (H7, M10), body-size limits (M7, M18), and cache headers (M17) are all added by individual handlers, so whatever a handler forgets is left open. *Design:* default-deny middleware. Reject any cookie-authenticated mutation without a CSRF token unless the route declares token-only auth, apply a global `MaxBytesReader` that routes can raise explicitly, send `Cache-Control: private` on every authenticated response, and rate-limit every credential check through one function.
4. **Other users can write into your space without consent.** iTIP REQUEST/CANCEL is applied straight into the recipient's calendar (H13), anyone can be added to groups or reached by `INSTANCE` shares (Low), and invitations auto-land with any RRULE. *Design:* whatever another user creates in your space should arrive as a pending item that you accept. Automatic application should be limited to updates from the party that already owns the object (the organizer of record).
5. **Untrusted content reaches tools that have the server's full privileges.** ImageMagick, Inkscape, LibreOffice, ffmpeg and yt-dlp run as the server user, with the whole data dir and the network available (H5, M16). `safehttp` exists but subprocesses bypass it. *Design:* run converters and fetchers in a sandbox (bwrap/nsjail: read-only bind of one input, no network, or network only through a proxy that enforces the safehttp policy). Make the safe client the only HTTP client plugins can obtain.
6. **Unbounded per-user state.** In-memory maps (Login Flow pending, chunk sessions, lockouts, direct tokens), push subscriptions, EventSource streams, calendar subscriptions, DAV resources and the search change queue have no caps or sweeps (M5, M10, M15, M18). *Design:* a per-user resource budget (counts as well as bytes) enforced by the storage layer, plus persistent state with TTL sweeps instead of process-local maps.
7. **Strings are formatted into protocols by hand.** Email headers (H12), `Content-Disposition` (Low), the SVG initials avatar (Low) and the Python source in the PSD converter (H5) are all built with `Sprintf`. *Design:* use typed builders (`net/mail`, `mime.FormatMediaType`, `mime.QEncoding`, `html/template`, argv), and lint for `fmt.Sprintf` feeding `Header().Set`.

## Design changes: status

The design changes proposed from these patterns, with where each stands. `internal/lint` holds source checks that run with `go test ./...` so a fixed pattern stays fixed.

- **D1 Username grammar — done.** `user.Store.ValidateUsername` is the one gate (`^[A-Za-z0-9][A-Za-z0-9._@+-]{0,63}$`, reserved data-dir names and plugin IDs, case-insensitive). `Create` is one statement, so names differing only in case and the first-admin race (Low) are both closed. Startup logs existing accounts that would now be refused. Closes the C1 attack; C1's longer-term half is D2.
- **D2 Store data by user ID — decided against.** Directories stay named by username, so admins can read them; D1 made that safe. Renaming stays a separate, explicit admin operation (not built): it would break clients' saved URLs, principal and attachment URLs held in other users' events and sent mail, and federated shares (`user@host`), none of which an ID-keyed layout would save.
- **D3 User deletion — done.** `Providers.DeleteUser` (admin UI and CLI) deletes the user's shares through the share store, then every row that refers to them in one transaction (owned groups lose their owner, owned volumes go with their mounts), closes their cached database handles and search index, and removes `data/<user>` and `data/<plugin>/<user>`. Closes H9.
- **D4 Verified, unique email — done.** `users.email` holds only confirmed addresses: a user's own change is pending (`email_verifications`) until they open the link mailed to it, signed in; an address an admin sets counts as confirmed; without SMTP a user cannot change it. One address, one account (`idx_users_email_unique` on `lower(email)`); migration029 clears addresses that several accounts shared. Closes H14. Addresses set before this are kept as they were.
- **D5 Hide the user directory — done.** `Providers.EmailVisible` (self, admins, users who share a group) governs OCS user lookups and DAV principals. Busy-only sharees get no description, dead props or listing, and no report but free-busy-query (as DESIGN/dav-storage.md already said); JMAP hides their events. `CS:source` is owner-only.
- **D6 Scheduling consent — done.** A REQUEST or CANCEL changes a copy only when the sender is its ORGANIZER, a REPLY speaks only for its sender and reaches only the organizer's copy, forged messages are dropped rather than left in the inbox, MANAGED-IDs not the sender's are stripped, and invitation email is capped per sender (`dav.Server.MailLimit`, 100/hour). Closes H13's overwrite and cancel. Invitations still land in the calendar, as clients expect, but the web calendar draws an unanswered one as a dashed outline and a declined one struck through (`cal-invite-pending`, `cal-invite-declined`) until answered or deleted. One event shows at most 1,000 instances per view (`maxViewInstances`); expansion itself still stops at 100,000 occurrences from DTSTART.
- **D7 Consent for shares and groups — done.** `share.Store.Create` refuses `INSTANCE` shares from non-admins and group shares from non-members who don't own the group. A group owner who is not an admin invites rather than adds; the user joins by accepting on their Groups page (`group_invitations.invitee_id`), and nesting a group needs rights over both. `share.Store.Decline` lets a user refuse a group or everyone share for themselves (`share_declines`, honoured by `ListBySubject` and `CheckAccessGrantedBy`); `CS:invite-reply` uses it.
- **D8 One storage service — done.** `internal/storage` hands plugins a `plugin.Storage` (`UserStorage`, `UserCache`, `GlobalStorage`) rooted in `os.Root`, so neither a name nor a symlink leads out of it; `DataDir()` and `UserFilesDir()` are gone from the plugin API, and `TestNoDataDirPaths` keeps paths into the data directory to the files that own its layout. A user's storage is counted in `storage_usage` and checked against their quota before a write replaces anything: calendar attachments, contact photos, recipe images, profanity lists and feed media, captions and cleaned audio (programs write into the cache; `Storage.Take` moves the result in). The feed collects media no download names any more. Caches hold previews, video thumbnails, fetched contact photos and models. Old locations move on first use. Local volumes go through `os.Root` too. The files plugin reaches files only through the user's VFS (previews work on every mount, M13), trash is a rename into `.cog-trash` at the root of the file's own mount, hidden by the mount FS, and trashed bytes count toward quota. Uploads are held to the room left plus the file replaced, failing before the rename (H3). Accounts made at runtime get their root mount when first resolved rather than at the next restart. Plugins enumerate users with `UsersOf` instead of listing the data directory (M12). SFTP, SCP and the shell (over SSH or `cog shell`) work in `files.Plugin.FS`, a VFS that holds writes to the quota as they are made and keeps the rows in step (H4); search reads file contents through the user's VFS too. Writers in progress (uploads, open handles and plugins' storage alike) draw on one per-user budget (`internal/quota/budget`) as their bytes arrive, so concurrent writes cannot each take what is left and nothing stages more than the quota allows. The quota checker is wired by `services`, so it holds whichever front end is running. Listing reconciles in both directions (M6). Caches are swept daily of what has gone unused for 30 days (a hit refreshes an entry), and thumbnails come in six sizes (M13). Nothing is opened or made for a deleted account's name until it is released.
- **D9 Default-deny HTTP — done.** `http.CrossOriginProtection` on every route (M11), `bodylimit` caps every body at 64 MiB unless the route is wrapped in `bodylimit.Unlimited` (uploads), authenticated responses are `Cache-Control: private` and `TestNoPublicCaching` keeps `public` to `internal/assets` (M17), and the server has header and idle timeouts. H10's unauthenticated plugin resource routes belong to D14.
- **D10 One credential check — done.** `ratelimit.Guard` checks Basic, Bearer, `/login`, MFA, SSH and public-link passwords: a client over the limit is refused, an account over it is slowed rather than locked, and a success clears only its own account (H7, M15 lockout DoS, M8). App passwords sign in only as their own user (Low). Registration and password-reset requests now count (M10). The auth and invitation-mail limiters keep their attempts in `rate_attempts` (`ratelimit.NewShared`), so a restart forgives nobody and replicas count together; a limiter that cannot count refuses. Only the per-account slowdown's serialising lock is per process.
- **D11 Credential lifecycle — done.** Resets (self-service link, admin, CLI) end sessions and app passwords; a password change offers to (H8). Sessions are stored as SHA-256 digests, upgraded on use (M1). CSRF uses a key derived from the master secret, and plugins get only that. The master secret lives in `<data dir>/.cog-secret` (0600), moved there from `system_settings` on first start; a backup must include it, or TOTP secrets cannot be read and links stop working. The VAPID key is still in the database.
- **D12 Sandbox runner — done.** `internal/sandbox` runs converters under bubblewrap when it can create namespaces: system dirs read-only, only the input and output paths bound, private /tmp, clean environment, no network except for yt-dlp. Inkscape, ImageMagick, Pillow, LibreOffice, tesseract, ffmpeg/ffprobe, whisper-cli and yt-dlp go through it; `TestProgramsAreSandboxed` keeps it so (`// unsandboxed:` for programs that read no upload). Where bwrap is missing or refused (Docker's default seccomp profile forbids the namespaces), programs run as before and the log, `cog doctor` and Admin > Plugins say so; `COG_SANDBOX=off` turns it off. Independent of the sandbox: SVGs linking outside themselves are not handed to Inkscape, LibreOffice gets a fresh profile per run with macros off, links never updated and no recalculation on load, and yt-dlp URLs must resolve to public addresses (`safehttp.CheckHost`). **Open:** yt-dlp can still follow a redirect or manifest to an internal address, since it makes its own connections; the published image needs its runtime to permit user namespaces for the sandbox to engage.
- **D13 safehttp only — done.** Every outbound client is safehttp's unless marked `// trusted URL:` (admin-configured), enforced by `TestHTTPClientsAreSafe`. safehttp connections fail after 60s without progress, and feed media is capped at 8 GiB. yt-dlp still fetches by itself (D12).
- **D14 Untrusted plugin isolation — done.** With `COG_PLUGIN_ORIGIN` set (`https://plugins.example.com`, or `https://*.plugins.example.com` for an origin per plugin, both served by this same listener), a process plugin's page renders as a document on that origin inside a sandboxed frame in the shell. The shell hands the frame a two-minute token (`auth.FrameToken`, signed with a key derived from the master secret); the origin turns it into a cookie of its own (`cog_frame`, `SameSite=None; Secure`, 12h) and signs the user in by that alone: the host's session, Basic and Bearer credentials are not consulted there. The origin serves only `/apps/<id>/` of that plugin and `/static/`; anything else, such as a redirect out of the plugin, is a page that asks the shell to navigate. Its responses carry `frame-ancestors <host>` and every cookie set there is rewritten cross-site. The frame reports its height and hands host links to the shell by `postMessage`, and the shell accepts only its own frame's origin and only host URLs. A process plugin runs as the server, so this isolates users' browsers, not the host. Unset, pages still render in the host and startup warns which plugins do.
- **D15 Per-user budgets — done except byte budgets.** Push subscriptions (100), EventSource streams (20) and DAV collections (200) are capped. Pending Login Flows (`login_flows`, tokens hashed, the app password sealed to the poll token) and direct-download tokens (`direct_tokens`, hashed, by file ID) are expiring tables, and a chunked upload's directory is its session, swept after a day idle, so none is lost on restart or confined to one replica. **Open:** byte budgets (D8).
- **D16 Typed builders — done.** `email.Message` validates addresses and encodes headers (H12; HTML parts now sent, `CreatePart` errors handled), `httphdr.Attachment` builds every `Content-Disposition`, the avatar escapes initials, and `TestNoFormattedHeaderValues` refuses `Sprintf` into a header.
- **D17 Process structure — done.** One service graph per process and idempotent `Close` (M3's double start), graceful shutdown on SIGTERM or `Run`'s context (M2). Search checks every shared result against current access when it is found (`share.Store.Readable`), dropping and un-indexing copies whose access went without an event (expiry, group removal, user deletion); copies are made and removed from `share.Store.OnChange`, so every way of sharing reaches recipients (M4). Only `cog serve` (and bare `cog`) starts process plugins: they register no commands or doctor checks, so every other command, the SSH login shell included, finds their binaries, keeping their IDs reserved, without starting them; plugin commands are collected only when the command line names no built-in command (M3). Copies follow the owner: every batch their index writes refreshes, or removes, the copies of what they shared (one share query per source), and a user whose index opens, or who joins a group, gains the copies they lack.

## Critical

- [x] **C1. Usernames are not validated, and the raw username builds storage paths (verified).** `user.Store.Create` (`internal/user/user.go:65`) accepts any string. The username goes into `db.PluginDBPath` (`internal/db/plugindb.go:20`, `filepath.Join(dataDir, username, …)`), the root mount subpath (`internal/web/admin.go:119`, `internal/mount/bootstrap.go:39`), the search index path, and several plugin directories. A self-registered user named `z/../victim` gets a root mount that cleans to `victim/files` and plugin DBs at `victim/app_data/…`, so they have full read/write access to the victim's files and every plugin database. The probe registered `z/../victim` and read the victim's file over WebDAV. This is reachable through `/register` (when registration is open), invite acceptance (`internal/web/groups.go:541`), admin creation, and the CLI. **Done** (D1).
  - Names can also collide with server-owned entries in the data dir: `app_data` (the registry's root data dir, `internal/plugin/registry.go:111`; user `app_data`'s home is `dataDir/app_data/files`, which is the files plugin's global dir), `avatars`, `.search`, and `cog-chunk-*` (chunk staging lives in `DataDir`). The feed orchestrator treats every directory in the data dir as a username (`plugin/feed/orchestrator/orchestrator.go:84`).
  - Fix: enforce a strict username grammar (e.g. `^[a-z0-9][a-z0-9._-]{0,63}$`, no `..`) plus a reserved-name list in `Create`. Longer term, key on-disk storage by user ID, not username. That also fixes H9 and makes renames possible.

## High

- [x] **H1. Directory trash/delete/rename uses `LIKE 'dir/%'`, which hits sibling directories (verified).** `plugin/files/trash.go:88`, `plugin/files/files.go:578` (HardDelete) and `files.go:648` (Rename children) build `path LIKE ?` from a raw path. SQLite `LIKE` is case-insensitive for ASCII and treats `_` and `%` as wildcards. Trashing `/Photos` deleted the metadata of `/photos/keep.txt` (verified). Renaming `/a_b` rewrites the paths of rows under `/aXb/`. Reconcile later re-adds the rows under new IDs, which breaks shares, favorites, comments and NC client file IDs. Fix: `substr(path, 1, length(?)) = ?` or a range comparison (`path >= 'dir/' AND path < 'dir0'`). **Done:** descendants are selected with `substr`, no `LIKE` remains in the files plugin.
- [x] **H2. Chunked uploads are assembled in lexical order (verified).** `internal/compat/chunked.go:241` sorts chunk names as strings. The NC v2 protocol allows unpadded numeric chunk names (`1`…`10000`), and Nextcloud sorts them numerically. Eleven chunks `1..11` assembled as `ajkbcdefghi`, which silently corrupts any upload with ten or more unpadded chunks. Related bugs in the same handler: **Done** (2026-11-06): numeric order when every chunk name is a number, `OC-FileId` from the file ID, `Destination` decoded and required under `/remote.php/dav/files/`, 507 on quota; sessions are directories (D15).
  - `OC-FileId` is built from the ETag instead of the file ID (`chunked.go:294`).
  - The `Destination` header is never URL-decoded (`chunked.go:224-232`), so `My%20File.txt` is stored literally.
  - A repeated MKCOL on the same transfer ID replaces the session without removing the old chunk dir (`chunked.go:124`). The old bytes stop counting toward staged quota but stay on disk forever, which bypasses quota and fills the disk.
  - Sessions are in memory only, so a restart orphans every `cog-chunk-*` dir in the data dir with no cleanup.
- [x] **H3. An over-quota overwrite destroys the original file.** `Files.Upload` (`plugin/files/files.go:346-379`) writes atomically over the existing file, then runs the quota check. On failure it deletes the path, which by then holds the replaced file. The old content is gone and the DB row still describes it. The check also counts the old and new sizes together on overwrite, so an edit near the quota is falsely rejected. Fix: check quota before the rename, using the size delta, and on failure remove only the temp file.
- [x] **H4. Quota can be bypassed by SFTP, SCP and the SSH shell, and disk usage is unbounded during uploads.** Fixed under D8: SSH works in the files plugin's FS, uploads stop at the quota as the bytes arrive, and concurrent writers share one budget.
  - Usage is `SUM(size)` from the files DB (`files.go:1185`). SFTP and SCP write through the VFS and never update that DB, so each file passes the check (`internal/ssh/sftp.go:83-98`) while the running total never grows until something lists the directory.
  - Shell redirects (`internal/ssh/shell/handlers.go:28`) and shell `cp`/`mv` have no quota check at all, and `/dev/zero` is available, so `cat /dev/zero > f` fills the disk.
  - `Upload` only pre-checks when given an `*io.LimitedReader`. WebDAV PUT and `/api/files/upload` pass `r.Body`, so the whole body is written to disk before any check.
  - Concurrent uploads race the check-then-write.
  - Fix: bound bodies with `Content-Length` or `OC-Total-Length` plus a `LimitReader` sized to the remaining quota, and count usage from a single source of truth.
- [x] **H5. Preview converters can read arbitrary local files into a thumbnail.** `plugin/files/preview.go:269-284`: **Done** (D12).
  - ImageMagick is called on `x.psd[0]` and `x.xcf[0]` without a coder prefix. ImageMagick sniffs the content, so an MVG/MSL/SVG payload named `.psd` gets coders like `text:@/path` and `label:@/path`, and the result lands in another user's or the server's view as a thumbnail.
  - Inkscape renders linked `<image href="/abs/path.png">` from SVG/AI/EPS, which reads other users' images from the shared data dir.
  - LibreOffice (`:354`) resolves linked content in documents.
  - All three run as the server user with access to the whole data dir and network.
  - The PSD path also splices paths into Python source with Go `%q`.
  - Fix: force coders (`psd:`/`xcf:`), ship a restrictive `policy.xml`, pass paths via argv, and run converters sandboxed (bwrap/nsjail, no network, read-only bind of the single input).
- [x] **H6. Decompression bombs crash the server.** **Done** (2026-11-06): `internal/safeimage.Decode` reads the header first and refuses more than 50 Mpx everywhere an upload is decoded (previews, avatars, contacts, gallery); archive entries and non-seekable files stream.
  - Viewing an archive entry reads the whole decompressed entry into memory (`plugin/files/pages.go:544`); a 10 MB zip entry that expands to 10 GB means OOM.
  - `image.Decode` runs without a `DecodeConfig` dimension check in thumbnails (`preview.go:195`), avatar upload (`internal/web/avatar.go`) and likely gallery, so a tiny PNG that declares 60000×60000 pixels has the same effect.
  - `serveContent` buffers whole files from non-local backends (`pages.go:305`), and archives on remote volumes buffer up to 500 MB per request (`pages.go:410`).
  - Fix: stream with `io.LimitReader` and cap entry sizes, check dimensions first, and use `http.ServeContent` only over seekable sources.
- [x] **H7. Basic-auth brute force bypasses the rate limiter.** `internal/auth/middleware.go:106-137` limits Basic and Bearer auth by IP only (no per-account key like `/login` has) and resets the IP counter on any success. An attacker with any valid account, or with open registration, interleaves one good login every nine guesses and gets unlimited password guesses against every non-MFA account, over WebDAV, OCS or any API. Fix: add a per-username key, and stop letting one account's success clear another's failures.
- [x] **H8. Password reset and password change leave app passwords and SSH keys active.** The reset (`internal/web/login.go:515`), the self-service change (`internal/web/settings.go:372`) and the admin reset revoke sessions only. App passwords minted through Login Flow and SSH keys an attacker added survive, so a reset does not lock out an intruder. The CLI `user passwd` (`cog_admin.go:152`) does not even revoke sessions. Fix: revoke app passwords on reset and offer to on change; list and confirm SSH keys and WebAuthn credentials.
- [x] **H9. Deleting a user fails, or leaves a trap.**
  - `shares.owner_user_id`, `groups.owner_id`, `volumes.owner_id` and `group_invitations.invited_by` reference `users(id)` without `ON DELETE CASCADE`, and foreign keys are on. Deleting anyone who ever shared a file, owned a group or invited someone therefore fails with a constraint error.
  - `adminHandler.DeleteUser` has already deleted the user's mounts outside the transaction (`internal/web/admin.go:222`), so the surviving user loses their root mount.
  - When deletion does succeed, plugin DBs and files remain on disk, keyed by username, and a new account with the same name inherits all of them, including calendars, notes and the search index.
- [x] **H10. The untrusted out-of-process plugin model does not isolate anything.** This matters before the "users install external plugins" TODO. **Partly done** (2026-11-06): the bridge drops `Cookie`, `Authorization` and `Proxy-Authorization` on the way in and `Set-Cookie` and hop-by-hop headers on the way out, process plugins get a token bound to the plugin (`auth.CSRFTokenFor`) and resource routes carry auth, user and CSRF; pages render on their own origin (D14).
  - The gRPC proxy forwards every request header, including `Cookie: cog_session` and `Authorization` (`internal/plugin/grpc.go:251`), plus the global CSRF token (`:266`).
  - It copies every response header back, so a plugin can `Set-Cookie` the session.
  - Page HTML is embedded raw into the same-origin shell (`internal/plugin/registry.go:834`).
  - Any such plugin therefore has full account takeover of every user who opens it.
  - Resource routes (`/apps/{plugin}/{type}/…`, `registry.go:971-984`) are mounted with no auth, no user context and no CSRF.
  - The request body is read unbounded (`grpc.go:244`).
  - Fix: strip credentials, give each plugin a scoped token, allowlist response headers, serve plugin UIs from a separate origin or iframe sandbox, and wrap resource routes in auth+CSRF.
- [x] **H11. Any `cog-plugin-*` executable on `PATH` is launched at startup, enabled by default.** `DiscoverProcessPlugins` (`registry.go:1179-1247`) treats "never configured" as enabled (`IsEnabled` defaults to true). A binary dropped in any `PATH` directory, including user-writable ones like `~/.local/bin`, runs on the next start. Fix: discovered plugins should default to disabled until an admin enables them. **Done** (2026-11-06): a plugin found on PATH and never configured is off unless named in `COG_TRUSTED_PROCESS_PLUGINS` (`*` for all, which `go tool dev` sets).
- [x] **H12. Email header injection and open mailing through calendar invites.** iMIP (`internal/dav/schedule.go:465-494`) builds `Subject:` from `SUMMARY`, where the iCalendar `\n` escape decodes to LF, and from the display name. `email.Send` writes `To:`/`Subject:` raw (`internal/email/email.go:96-99`). Any user can make the server send mail with arbitrary headers and body to arbitrary external addresses under its SMTP identity, with no rate limit. Fix: reject CR/LF in header values, RFC 2047-encode subjects (which also fixes non-ASCII subjects), validate addresses with `mail.ParseAddress`, and rate-limit outbound invites.
- [x] **H13. Any user can overwrite, cancel or plant events in any other user's calendar through iTIP (verified).** `Server.deliver` → `apply` (`internal/dav/schedule.go:289-355`) looks up the recipient's event by the message's `UID` alone and hands it to `itip.Apply` (`internal/dav/itip/itip.go:573`). `applyRequest` and `applyCancel` never check that the sender is the organizer of the copy they change. **Done** (D6).
  - In the probe, bob (no access to alice's calendars) PUT an event in his own calendar with `UID:secret-1`, `SEQUENCE:99`, `ORGANIZER:bob`, `ATTENDEE:alice`. Alice's private event `secret-1` was replaced with bob's content.
  - Deleting that event instead sends a CANCEL that marks the victim's event `CANCELLED`, even when the victim is its organizer. UIDs are not secret: every attendee of a meeting knows its UID.
  - REQUESTs from anyone are also auto-added to the recipient's default calendar with no consent, so any user can fill another's calendar. The events can carry rules like `FREQ=SECONDLY`, each expanding to 100,000 instances (`maxInstances`) on every calendar view. The same path stores whatever `ATTACH`/`MANAGED-ID` the sender supplied.
  - Fix: apply a REQUEST or CANCEL only when there is no current copy, or when the current copy's ORGANIZER matches the sending user's address. When there is no current copy, put the message in the inbox as pending (or limit auto-add to senders the recipient has accepted before). Rate-limit invitations per sender, and strip `MANAGED-ID` from received objects.
- [x] **H14. Email addresses are unverified and not unique, but they decide scheduling identity (verified).** `users.email` has no UNIQUE constraint (`internal/db/sql/schema.sql:10`), and changing it requires only your own password (`internal/web/settings.go:316`). `GetByEmails` resolves a shared address to the first user by username (`internal/user/user.go:207`).   - organize as bob (`ORGANIZER:mailto:bob`), and the server sends it to local users and by iMIP to external addresses;
  - send REPLYs as bob, which change bob's PARTSTAT on other organizers' events;
  - pass `mayFetch` as an attendee (`internal/dav/attach.go:228`) and read attachments of events bob is invited to.
  - Fix: verify an address by emailed link before it counts for anything, enforce `UNIQUE(lower(email))`, and refuse an ambiguous resolve instead of picking one.

- [x] **M1. Session tokens are stored in plaintext.** `sessions.id` is the bearer token (`internal/auth/session.go:110,148`). Every other token is hashed, and the prior audit doc says sessions are too. Combined with sliding sessions that never expire, a DB backup or leak means live sessions indefinitely. Store `HashAtRest(token)` and keep the cookie as the raw value. The CSRF token is HMAC(session ID), so derive it from the hash or keep a separate handle.
- [x] **M2. The HTTP server has no timeouts and no graceful shutdown.** `http.ListenAndServe` (`cog_serve.go:75`, `cog.go:235`) means no `ReadHeaderTimeout`, so it is open to slowloris. - [x] **M3. `cog` builds two full service graphs, and every CLI command spawns plugins.** `Main` calls `addPluginCommands` → `services.New` → `DiscoverProcessPlugins` before parsing args (`cog.go:137,148`, `internal/services/services.go:279`). `cog serve` then builds a second `Providers`. - [x] **M4. Search propagation of shared items leaks after revocation and goes stale.** Shared documents are copied into recipients' indexes, but only the OCS sharing handler and the generic share UI call the propagator (`internal/web/routes.go:282`, `internal/web/share_handler.go:480`). Shares created or deleted via `/api/shares`, DAV sharing, plugin `ShareStore`, expiry, group membership removal and user deletion never propagate. Recipients keep searching content they no longer have access to. Copies are snapshots, so owner edits never reach them either. Hooking `share.Store.OnChange` covers creates and deletes. - [x] **M6. Files metadata only follows writes made through the files plugin.** Fixed under D8: SSH writes through the plugin, uploads record the folders they make, and `reconcile` updates changed files (by size or on-disk mtime) and forgets those gone.
  - SFTP, SCP, the shell and other plugins write to disk directly. `reconcile` (`files.go:686-776`) only inserts new rows: it never removes rows for deleted files and never updates size, mtime or ETag for changed ones. NC/WebDAV clients never see those edits (the ETag is unchanged), quota and search are wrong, and deleted files linger.
  - `Upload` also creates no metadata rows for missing parent directories, so `DELETE` of a parent made implicitly by `PUT /a/b.txt` returns 404 until something lists the root (seen while probing H1).
  - Fix: route all writers through one API, or have reconcile compare stat data in both directions.
- [x] **M7. WebDAV correctness** (`internal/compat/webdav.go`): **Partly done** (2026-11-06): `extractPath` no longer decodes twice, `Destination` is cut at `/remote.php/`, decoded and must be under the files root, COPY and MOVE refuse the root and into-self, PUT answers 507 on quota.   - GET has no Range support (`:229`, and the direct-download endpoint the Android media player uses); `http.ServeContent` would provide it.

Public-link password lockout trusts `X-Forwarded-For` from anyone.** `clientIPForLockout` (`plugin/files/api.go:891`) takes the leftmost XFF value, so an attacker rotates it to get unlimited share-password guesses. Separately, the password can be sent in `?password=`, which ends up in access logs. **Done:** the guard keys on `ratelimit.ClientIP` (trusted proxies only) and the password travels as Basic auth; a `?password=` query is ignored and logged.

If `SetPassword` fails, the error is returned but the open link remains. **Done** (2026-11-06): the hash goes in the same INSERT.
- [x] **M10. Registration has effectively no rate limit.** `HandleRegister` checks `IsLimited(ip)` but never records anything (`internal/web/login.go:323-331`), so open registration allows unlimited account creation. Login Flow `HandleInit` is unauthenticated and unlimited (`internal/compat/login.go:69`), so its in-memory pending map can be grown to exhaustion within each 10-minute window. **Done** (D10; Login Flow init counts since 2026-11-06).
- [x] **M11. JSON and OCS mutation APIs have no CSRF check.** `/api/files/*`, `/api/shares*` (`plugin/files/api.go:61-89`), OCS sharing, and `RegisterRoute` routes accept cookie sessions with only `SameSite=Lax` as protection. A text/plain cross-site POST to `/api/files/upload` with cached Basic credentials overwrites files. - [x] **M12. Plugins build their own DB paths, against the CLAUDE.md rule.** `plugin/feed/orchestrator/orchestrator.go:88`, `plugin/gallery/scanner.go:64` and `plugin/gallery/gallery.go:289,351` hand-build `…/app_data/<plugin>/plugin.db`. - [x] **M13. Previews ignore mounts and leak caches into user space.** Fixed under D8: previews read through the VFS and cache in the user's uncounted cache, which is swept daily; requested sizes round to six. `Preview`/`PreviewPDF` read `filepath.Join(UserFilesDir, path)` (`preview.go:168,178,336`), so files under any non-root mount get no preview, or a shadowed file's preview. `convertToPNG` writes its cache to `filepath.Dir(src)/../converted` (`:251`), which lands inside the user's own file tree for nested paths, shows up in listings and counts against quota. The thumbnail, converted and preview caches are never pruned, and each requested size (16–1024) is cached separately.
- [x] **M14. Per-request mount resolution is expensive.** Every files operation calls `p.userFS(username)` → `Resolver.UserFS`, which re-reads the user, all mounts, each volume and share access, and builds new backends. `Upload` does that 2–3 times. `EnsureRootDir` runs on every API and WebDAV request (two `MkdirAll` calls, mount resolution and an INSERT). Quota checks look the user up twice and `SUM` the files table on every write. Cache the per-request FS and the root-dir check. **Done** (2026-11-06): `mount.Resolver` keeps each user's VFS until a mount, volume or share changes (`Store.Changed`, `share.OnChange`) or 30s pass.
- [x] **M15. Lockout DoS and limitations of the in-memory limiter.** Per-account keys let anyone lock any user out of `/login` and SSH with 10 bad attempts per 15 minutes. Behind a reverse proxy without `COG_TRUSTED_PROXIES`, every client shares one IP, so 10 failures lock out everyone. - [x] **M16. Feed fetching escapes the SSRF guard, and media downloads are unbounded.** **Mostly done** (D12, D13); open: yt-dlp redirects. **Done** (D12, D13; since 2026-11-06 yt-dlp fetches through `safehttp.Proxy`, a loopback proxy that checks every connection it makes, redirects included).

- [x] **M18. Authenticated users can exhaust resources with no per-user caps.** **Done** (D9 body limit, D15 caps, D8 quota) except DAV object bytes, which are D22; "Export all" streams since 2026-11-06.

  - WebDAV-Push and JMAP push subscriptions are unlimited per user (`internal/push/store.go:143`). Every change then sends a POST to each registered HTTPS endpoint, so one account can make the server send requests to any public HTTPS host.

# Audit findings — 2026-11-06

Third pass, on `storage-service` @ `60bacf72`, after the first two rounds (above). It re-read the auth chain, routing and middleware, the files plugin and its API and pages, WebDAV, chunked uploads, trashbin and comments, sharing (store, OCS and web), federation, Login Flow, storage, VFS, volumes and mounts, SSH, the plugin registry and gRPC bridge, the settings, login, group and admin handlers, rate limiting and the secrets and MFA stores. It did not re-read `internal/dav`, `internal/jmap` or the non-files plugin pages, which the second pass covered.

## Design changes

- **D18 Federation names its peers — done.** An empty allowlist federates with nobody; `*` is the admin's explicit choice to accept shares from any server, and the admin page says what that means. Before storing an inbound share the receiver fetches the claimed sender's `/.well-known/ocm-provider` through safehttp (10s) and refuses a host that answers nothing or has federation off: OCM 1.1 signs nothing, so this is the most the protocol allows. A user holds at most 100 pending inbound shares (`MaxPendingInbound`).
- **D19 Process plugins are trusted by the admin, not by PATH — done.** Found-but-unconfigured is off (H11). A process plugin has code execution as the server, so "trusted" (host secrets, system DB) and "enabled" are the admin's call; `COG_TRUSTED_PROCESS_PLUGINS=*` is for development and `go tool dev` sets it. The in-browser boundary is D14.
- **D20 Outbound mail is a budget — done for invitations.** Group invitations validate the address (`mail.ParseAddress`, address only) and draw on the same per-sender limiter as calendar invitations (`DAV.MailLimit`, 100/hour). Anything else that sends mail on a user's say-so should go through the same limiter.

## High

- [x] **N1. Anyone could fill any user's pending federated shares.** `POST /ocm/shares` took the sender's host from the attacker-written `owner` field, so with federation on and no allowlist every server on the internet could create pending shares with any name for any local user, without limit. Done under D18.
- [x] **N2. Group invitations were an open mailer.** Any user could create a group and `POST …/invites` to any address; the server mailed it under its own identity with the group's name as content, with no address check and no limit. Done under D20.
- [x] **N3. The federation WebDAV proxy copied every remote response header, `Set-Cookie` included** (`internal/federation/webdav_proxy.go`), so a peer could set `cog_session` on this origin, and it read PROPFIND bodies unbounded. Nothing called it. Deleted.
- [x] **N4. The gRPC bridge.** See H10: credentials crossed the socket in both directions, resource routes had no auth and plugins held the session-wide CSRF token. Done except the shell (D14).

## Medium

- [x] **N5. `/ocs/…/profiles/{user}` returned any user's email to any signed-in user**, around D5. Gated by `EmailVisible`.
- [x] **N6. `/index.php/avatar/{user}/{size}` was unauthenticated** and told initials from `?`, enumerating usernames; initials went into the SVG unescaped. Now `RequireAuth` and escaped.
- [x] **N7. Comments were unbounded** (a 64 MiB body became a row, re-read on every listing). Capped at 16 KiB, 413 beyond.

## Design changes, second round

- **D21 Agents — done.** An agent is a user account with an owner (`users.owner_id`): it has no password, signs in only with app passwords its owner issues, and reaches exactly what a user who received a share reaches, through the same shares (`share.Store` refuses a share made by an agent). Its changes carry its name. The Login Flow grant page offers "sign the app in as me / an agent / a new agent"; Settings › Agents creates agents, issues and revokes their tokens (shown once) and deletes them; admins see agents among the users with their owner, since agent names share the username namespace. Deleting an owner deletes their agents. Existing app passwords are unchanged: they are the user's own.
- **D22 DAV object bytes count toward quota — done.** Every DAV table keeps each resource's rendered size, so `dav.Table.Usage` recounts it with one `SUM` per backend, `dav.Server.Usage` adds the backends, and `Providers.StorageUsage` adds that to files and plugin storage. A recount cannot drift; a deletion shows at once.
- **D23 Password policy — done.** `internal/password`: a minimum length (default 8) and a Pwned Passwords check by k-anonymity, both set on the admin settings page; `user.Store` asks the policy before storing any password, and an unreachable breach list refuses rather than sets unchecked. Existing passwords are checked at their next change.
